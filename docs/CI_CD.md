# CI / CD — `ys_userapp`

This document explains the GitHub Actions setup, what each workflow does,
which secrets are required, and how to cut a release.

---

## Overview

| Workflow file | Trigger | What it does |
|---|---|---|
| [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) | Every push to `main` / `develop`, every PR targeting them | `flutter pub get` → format check → `flutter analyze` → `flutter test` → build a debug APK (smoke check) and upload as a 7-day artifact |
| [`.github/workflows/release-android.yml`](../.github/workflows/release-android.yml) | Manual (`workflow_dispatch`) **or** pushing a tag matching `v*.*.*` | Builds signed release APK + AAB, uploads them as workflow artifacts, optionally distributes the APK to Firebase App Distribution, optionally creates a GitHub Release with the binaries attached |

Concurrency cancellation is enabled — pushing a new commit cancels the in-flight CI run for the same branch / PR, so you don't burn runner minutes on stale work.

---

## Required tooling

The workflows pin:
- **Flutter `3.38.9`** (stable channel) via [`subosito/flutter-action`](https://github.com/subosito/flutter-action). Bump in both YAML files when the team upgrades.
- **Java `17` (Temurin)** for Android Gradle Plugin.
- **Ubuntu latest** runner — sufficient for Android. iOS builds would need `macos-latest`; see [Adding iOS](#adding-ios-later) below.

## GitHub secrets

All secrets live under **Repo → Settings → Secrets and variables → Actions → New repository secret**.

### Required for any release build

| Name | Purpose |
|---|---|
| `GOOGLE_MAPS_API_KEY` | Passed as `--dart-define=GOOGLE_MAPS_API_KEY=...` to the build. Read it in Dart via `String.fromEnvironment('GOOGLE_MAPS_API_KEY')`. |

### Required to produce a Play-Store-uploadable build

| Name | Purpose |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | The upload keystore (`.jks`), base64-encoded. Generate locally with `base64 upload-keystore.jks > keystore.b64` and paste the contents. |
| `ANDROID_KEYSTORE_PASSWORD` | Keystore password. |
| `ANDROID_KEY_ALIAS` | Key alias inside the keystore. |
| `ANDROID_KEY_PASSWORD` | Password for that specific key (often same as keystore password). |

If these aren't set, the release workflow still runs — it just builds with the **debug keystore**, which is fine for Firebase App Distribution testing but **not** uploadable to the Play Store.

### Required to auto-distribute to Firebase App Distribution

| Name | Purpose |
|---|---|
| `FIREBASE_APP_ID_ANDROID` | The Android App ID from Firebase console (looks like `1:1234567890:android:abcdef...`). |
| `FIREBASE_TOKEN` | A CI token generated by running `firebase login:ci` locally and copying the printed token. |

And one repository **variable** (not secret — visible in YAML):

| Name | Purpose |
|---|---|
| `FIREBASE_TESTERS` | Comma-separated list, e.g. `qa@yellowspottech.com,mahesh@yellowspottech.com`, or a tester group name like `internal-qa`. |

## How CI runs on PRs

1. PR opened against `main` / `develop`.
2. `ci.yml` runs the `analyze-and-test` job:
   - `flutter pub get`
   - `dart format --output=none .` (currently non-blocking — flip to `--set-exit-if-changed` once the codebase has been formatted once)
   - `flutter analyze` — **must pass**
   - `flutter test --reporter expanded` — **must pass**
3. If that succeeds, `build-android-debug` builds an unsigned debug APK and uploads it as an artifact named `app-debug-<sha>`. Reviewers can download and install it on their phone to smoke-test the PR.

A failed step blocks merge if you enable branch protection (recommended — see [Branch protection](#branch-protection)).

## How to cut a release

### Option A — Push a version tag (recommended)

1. Bump `version:` in [`pubspec.yaml`](../pubspec.yaml). Format is `<semver>+<buildNumber>`, e.g. `1.2.0+12`.
2. Commit and push.
3. Tag and push the tag:
   ```bash
   git tag v1.2.0
   git push origin v1.2.0
   ```
4. `release-android.yml` triggers automatically:
   - Builds **both** APK and AAB in release mode.
   - Signs with the upload keystore (if secrets are configured).
   - Uploads both as workflow artifacts (30-day retention).
   - Distributes the APK to Firebase App Distribution (if `FIREBASE_APP_ID_ANDROID` + `FIREBASE_TOKEN` are set).
   - Creates a **GitHub Release** named after the tag, with the APK + AAB attached and auto-generated release notes (commit list since the previous tag).

### Option B — Manual trigger

1. Go to **Actions → Release Android → Run workflow**.
2. Pick a branch.
3. Choose `build_type` (`apk`, `appbundle`, or `both`) and whether to distribute to Firebase.
4. Click **Run workflow**.

No GitHub Release is created in manual mode — only artifacts (and optional Firebase distribution).

## How signing works under the hood

The workflow:
1. Decodes `ANDROID_KEYSTORE_BASE64` into `android/app/upload-keystore.jks`.
2. Writes `android/key.properties` with the four password / alias fields.
3. [`android/app/build.gradle.kts`](../android/app/build.gradle.kts) reads `key.properties` at configuration time:
   - If present → defines a `release` signing config and uses it for the `release` build type.
   - If absent → falls back to the `debug` signing config so `flutter run --release` still works on machines without prod keystores.

Both `android/key.properties` and any `.jks` files are gitignored — they should never be committed.

### Local-only release builds

If you want to produce a signed release APK on your own machine:

```bash
# one-time: drop your keystore at android/app/upload-keystore.jks
# and create android/key.properties:
cat > android/key.properties <<EOF
storeFile=upload-keystore.jks
storePassword=<your_store_password>
keyAlias=<your_alias>
keyPassword=<your_key_password>
EOF

# then:
flutter build apk --release --dart-define=GOOGLE_MAPS_API_KEY=<your_key>
# or for Play Store:
flutter build appbundle --release --dart-define=GOOGLE_MAPS_API_KEY=<your_key>
```

## Branch protection (recommended)

Under **Settings → Branches → Branch protection rules**, add a rule for `main`:

- ☑️ Require a pull request before merging
- ☑️ Require status checks to pass before merging
  - `CI / Analyze & test`
  - `CI / Build Android (debug smoke)`
- ☑️ Require branches to be up to date before merging
- ☑️ Do not allow bypassing the above settings

Same rules apply to `develop` if you use git-flow.

## Adding iOS later

iOS builds need a `macos-latest` runner (slower, more expensive minutes) and one of:
- An **Apple Developer account** + **distribution certificate + provisioning profile** stored as secrets, or
- A managed signing service like **Fastlane Match** or **App Store Connect API key**.

When you're ready, add a sibling workflow `release-ios.yml` with the broad shape:

```yaml
jobs:
  build:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: '17' }
      - uses: subosito/flutter-action@v2
        with: { flutter-version: '3.38.9', channel: stable, cache: true }
      - run: flutter pub get
      # ── Decode certs + provisioning profile from secrets here ──
      - run: |
          flutter build ipa --release \
            --dart-define=GOOGLE_MAPS_API_KEY=${{ secrets.GOOGLE_MAPS_API_KEY }} \
            --export-options-plist=ios/ExportOptions.plist
      - uses: actions/upload-artifact@v4
        with:
          name: app-release-ios
          path: build/ios/ipa/*.ipa
```

The detailed signing dance is best done with a third-party action like [`apple-actions/import-codesign-certs`](https://github.com/apple-actions/import-codesign-certs) — happy to wire it up when the certs are ready.

## Adding Play Store upload later

When the team is ready to publish to the Play Console automatically, add this step to `release-android.yml` after the AAB upload:

```yaml
- name: Upload AAB to Play Console (internal track)
  if: ${{ github.event_name == 'push' && startsWith(github.ref, 'refs/tags/') }}
  uses: r0adkll/upload-google-play@v1
  with:
    serviceAccountJsonPlainText: ${{ secrets.PLAY_SERVICE_ACCOUNT_JSON }}
    packageName: com.example.yellowspotuser   # ⚠️ change to your real applicationId first
    releaseFiles: build/app/outputs/bundle/release/app-release.aab
    track: internal
    status: completed
```

Prerequisites:
1. **Rename the package** — currently `com.example.yellowspotuser` in [`android/app/build.gradle.kts`](../android/app/build.gradle.kts). Play Store requires a unique, non-`com.example.*` id (e.g. `com.yellowspottech.userapp`).
2. Create a Google Play service account, grant it the **Release Manager** role, download the JSON key, paste into `PLAY_SERVICE_ACCOUNT_JSON`.
3. Manually upload the first build through the Play Console UI (the action can't create the listing itself).

## Troubleshooting

### `Permission denied` writing `android/app/upload-keystore.jks` in CI
Usually means `ANDROID_KEYSTORE_BASE64` is empty or contains whitespace. Regenerate with `base64 -w 0 upload-keystore.jks` (no line wrapping) and re-paste.

### Build succeeds locally, fails in CI with `GOOGLE_MAPS_API_KEY` errors
The dart-define isn't reaching the build. Confirm the secret name matches exactly (`GOOGLE_MAPS_API_KEY`, not `GOOGLE_MAPS_KEY`), and that you're reading it in Dart via `String.fromEnvironment('GOOGLE_MAPS_API_KEY')` rather than `Platform.environment`.

### `flutter analyze` fails on `withOpacity` deprecation
Pre-existing in `lib/features/parking/**`, `lib/features/residential/**`, `lib/features/services/**`. These are `info`-level lints, not errors — `flutter analyze` will still exit 0. If they ever flip to warnings, run `dart fix --apply` to bulk-migrate to `withValues(alpha: ...)`.

### CI build takes >15 min on a fresh runner
The first run downloads the Flutter SDK. Subsequent runs use the cached SDK (`cache: true` on `flutter-action`) and should drop to ~5 min.

### Firebase distribution step is skipped silently
Check the `if:` condition in the YAML. It requires **both** `FIREBASE_APP_ID_ANDROID` to be set as a secret **and** either a tag push or `distribute: true` in the manual trigger.
